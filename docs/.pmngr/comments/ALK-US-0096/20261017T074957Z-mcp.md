Fixed in commit b9f0371. Root cause (reproduced with llama-server b11669 alone, `-v`): the GGUF Jinja template of qwen2.5-coder:0.5b is byte-identical to llama.cpp's tested Qwen2.5-7B template, the autoparser detects `tool_mode: JSON_NATIVE` with `<tool_call>`, and `--jinja` is passed. But llama.cpp's JSON-native tool parser allows `optional(content(until("<tool_call>")))` before the calls even with `tool_choice: required`, so the grammar lets the 0.5B model write the JSON bare; it can never end (EOS forbidden before a call) and runs to max_tokens.

Fix (ADR 0005, docs/development/decisions/0005-forced-tool-call-prefill.md): for forced choices (OpenAI `required`/named, Anthropic `any`/`tool`, Responses) on Hermes-style JSON templates (`<tool_call>` without `<function=`), `alkahest_api::tool_prefill` appends an assistant prefill `<tool_call>\n`, which llama-server feeds to the grammar; named choice narrows `tools`; `parallel_tool_calls` defaults to false. No per-model override needed for this model; models whose template has no tool format still need a `template` override.

Tests: unit `tool_prefill::tests::*`, `tests/openai.rs#forced_tool_choice_prefills_hermes_marker`, real `crates/alkahest/tests/serve_tools.rs` (OpenAI required -> `get_weather({"city":"Paris"})`, finish `tool_calls`; streamed named choice; Anthropic `any` -> `tool_use`) passed; `scripts/conformance.sh --url ... --chat qwen2.5-coder:0.5b` with `ALKAHEST_CONFORMANCE_TOOLS=1`: ollama, openai (incl. Responses function_call) and anthropic all checks passed. Change record: docs/development/changes/2026-10-17-forced-tool-call-prefill.md
